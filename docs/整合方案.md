# B站鱼娘 设计与实施记录（dsh-bili-scroll）

> 项目：**B站鱼娘**（插件包名 `dsh-bili-scroll`；安装命令与家目录都不变）。
> 本文是 2.1 的设计与实施记录：前面几节保留设计阶段对相关开源项目的评估，作为决策依据；后面几节是落地进展。

> 版本：草案 v1 · 2026-10-22
> 依据：`_ref/scroll`（dsh-bili-scroll 2.0.0）、`_ref/whale`（dsh-bili-whale 0.4.5）两份 main 分支快照，
> 以及本机已装环境（`dsh-bili-scroll@0.1.7` + `@xmanrui/dsh-im@5.2.0`，DSH `0.2.1-rc.2`）。
> 文中「事实」= 已读代码/文档确认；「判断」= 我的推断；「待验证」= 需要跑一次才能定。

## 0. 结论先行

**推荐「方案 A · 一个她」**，分四期落地：

以现有的 **dsh-bili-scroll 插件壳**（扫码登录、四页签设置页、日报卡片墙、私信投递、注入防线）为基础，
补齐**能力层**（Node 工具链、生物钟、分享闸门、两本日记、草稿审核、通知后端），
统一成 **一份配置、一个数据目录、一个常驻会话**，最后挂上 **云桥**。

三个关键判断：

| 判断 | 理由 |
|---|---|
| **运行形态选常驻会话（whale 那条）** | 云端群聊要"同一个 AI、信息互通"，就必须有连续的"她"；scroll 每轮起一次性会话，天生没记忆 |
| **能力层要 Node 化（whale 那条）** | scroll 自己 README 的路线图就写着"用 JS 重写 search/subtitle/comments/reply ⇒ 不再需要 Python"；Python/uv 链路是它最大的安装失败源 |
| **壳和 UI 留 scroll 的** | 扫码登录比手抄 SESSDATA 强一个量级；日报 + 卡片墙是 whale 没有的；这也是"以 scroll 为主"的意思 |

**云桥不是从零发明**：本机已装 `@xmanrui/dsh-im@5.2.0`，它提供 `ctx.dshIm.send()`（九个渠道出站）
和 `POST /api/dsh-im/delivery/messages`。所以云桥 = **协议 + 适配器**，出站今天就能真发到群，
入站等云端开发完只需实现一个 adapter。

## 1. 两边现在各是什么

| 维度 | **dsh-bili-scroll 2.0.0**（刷B站） | **dsh-bili-whale 0.4.5**（养鱼） |
|---|---|---|
| 一句话 | 每天替你刷一轮，挑出值得的，@ 你 | 一条有日子的鱼：自己按作息醒、看懂、写两本日记 |
| Host 半端 | `index.js` 2235 行 + `client.js` 826 行 | `lib/index.js` 533 + `scheduler.js` 597 + `client.js` 602 |
| 宿主服务依赖 | `inject: ['webServer','tools','settings']`；20 个 HTTP 接口挂在 `/api/bili-duty` | `inject: ['sessionController','webServer','connection']` ⇒ **headless 起不来** |
| 运行形态 | **每轮 spawn** `process.execPath <dsh>/lib/bin.js --profile <headlessProfile> --patch <overlay> <prompt>`，cwd = 插件家目录 | **常驻会话** `bili-whale`（cwd `~/.dsh/whale-work`），`sessionController.prompt(mode:'queue')` 唤醒 |
| 能力层 | Python MCP（内置 `bilibili-mcp` 共 27 个工具，白名单只放行 `search/subtitle/comments/video_info` + 条件放行 `reply` / `send_message`） | 纯 Node CLI `tools/bili.mjs`，约 30 个子命令 |
| 看内容 | 字幕原文（可选 Whisper 本地转写） | 字幕 + 弹幕热区 + 热评 + **抽帧看画面** + 硬字幕裁条（`debrief --substrip`） |
| 调度 | 峰谷窗口（12–14 / 18–09）+ 每日额度 `perDay` | **生物钟**：窗口内随机时刻 + 30% 概率"今天不看" + 跨午夜 + 计划持久化 |
| 记忆/产物 | `out/<日期>.md`、`digest/<月>.md`、`seen.md` 判重表 | 两本日记（给主人 / 给自己）+ `whale-log.jsonl` + `quota.json` |
| 投递 | 评论 @ / B站私信（`dmMode` off·only·both） | 评论 @ / 私信 / notify 七后端（`none·desktop·webhook·command·dm·stdout·file`） |
| 人格 | 工作区 `AGENTS.md` 内联 + `personaPrompt` 框 | `~/.bili-ai/persona.md`（取前 3000 字）+ 三字段（角色名/称呼/自称） |
| 克制/闸门 | 每轮评论条数、同视频只评一次 | 分享 ≤3/天、同视频 7 天一次、评分 ≥13/20、沉默 7 天归零、撞风控停手 |
| 审核 | 无 | `pending-replies.json` + 设置页批准/否决 |
| 数据目录 | `$DSH_HOME/bili-duty/` | `~/.bili-ai/` + `~/.dsh/bili-whale.config.json`、`whale-night.json`、`whale-log.jsonl` |
| 安装门槛 | 需要 **Python 3.10+ 或 uv**（插件可自下 uv） | 需要 **Node**（插件自找真 node.exe）+ 可选 ffmpeg；**手动抄 cookie** |
| 测试 | `selfcheck.mjs` 自检 | `node --test`，5 个文件 **67 个用例**；但只 mock 到 `apply(ctx)` 这一层，没有可复用的宿主抽象 |

**一句话对照**：scroll 的**壳、安装体验、交付物**更强；whale 的**内核、克制、记忆**更强。

## 2. 两个项目各自的优化点

### 2.1 scroll 要补的

| 优先级 | 问题 | 优化 | 来源 |
|---|---|---|---|
| **P0** | Python venv / uv / 镜像 / 杀软，是安装失败的头号原因 | 能力层 Node 化，Python 只保留 ASR 一条可选支线 | whale 的 `tools/` |
| **P0** | 判重与配额靠"报告里 `### BV号` 行数"这种**文本约定**，模型漏写就记错账 | 改成**结构化账本**（`ledger/*.json`），模型只报事实、宿主记账 | whale 的 `quota-gate` / `store` |
| **P1** | 固定峰谷窗口 ⇒ 每天同一时刻，像打卡；没有"今天不想看" | 生物钟：窗口内随机 + 30% 跳过 + 跨午夜 + 计划持久化 | whale `lib/scheduler.js` |
| **P1** | 发评论没有评分闸门，靠提示词自觉 | 分享闸门：分数 ≥13、同视频 7 天、每天 ≤3、沉默衰减 | whale `share-policy.mjs` |
| **P1** | 只会"发评论/私信"，没有别的出口 | 通知后端五种（桌面/Webhook/命令/文件/私信），Webhook 自动适配飞书·钉钉·企微·QQ | whale `commands/notify.mjs` |
| **P1** | 陌生人回复直接发，没有二审 | 草稿队列 + 设置页批准/否决 | whale `pending-replies` |
| **P2** | 只看字幕，"看懂"有限 | 弹幕热区 + 抽帧 + 硬字幕裁条 | whale `debrief.mjs` / `video-content.mjs` |
| **P2** | 每轮一次性会话 ⇒ 无记忆、人格不连续 | 常驻会话 + 状态卡（第 5.4 节） | whale 会话形态 |

### 2.2 whale 要补的

| 优先级 | 问题 | 优化 | 来源 |
|---|---|---|---|
| **P0** | 手抄 `SESSDATA`（HttpOnly，必须 F12 抠）⇒ 门槛高、易错 | 改**扫码登录**，凭证落本机 | scroll `lib/login.mjs` + `qrcode` |
| **P0** | 必须 web profile（`sessionController` 缺失就 pending 不启动） | 加**降级路径**：没有 `sessionController` 时退回 spawn 一次性会话 | scroll 的 run-a-round |
| **P1** | 只有文字/日记，没有"它刷过的视频"视图 | 日报卡片墙 + 档位筛选 + 分页 | scroll `out/*.md` 解析 + `client.js` |
| **P1** | 配置散在 5 个文件、4 个目录 | 合并为单一只读真相源 + 迁移器 | 本方案第 5.3 节 |
| **P1** | 常驻会话上下文无限增长（每天醒来都往同一会话里堆） | 每轮注入**状态卡** + 定期 compact + 事件流外置 | 本方案 5.4 |
| **P2** | 网络/风控失败的报错偏内部 | 统一错误码（`bot-not-connected` 那种风格）+ 设置页"测一下" | scroll `verify.mjs` |

### 2.4 两边都缺的（就是你要的第三个功能）

- **没有一个"跨端共享的灵魂层"**：人设、记忆、配额、审核队列都困在单机单插件里。
- 云端群聊机器人一旦上线，会出现三个"她"各说各话：本地插件一个、B站评论区一个、群里一个。
- ⇒ 这一块单独设计，见第 6 节。

## 3. 必须拍板的四个分歧

| 分歧 | scroll 的做法 | whale 的做法 | **建议** | 理由 | 代价 |
|---|---|---|---|---|---|
| **① 运行形态** | 每轮 spawn 一次性 headless 会话 | 常驻会话 + prompt 注入 | **常驻会话**，保留 spawn 作降级 | 云同步要求"同一个她"；省掉每次 spawn dsh 的进程/启动开销 | web profile 依赖变强；要防上下文膨胀 |
| **② 能力层语言** | Python MCP | 纯 Node CLI | **Node 为主**，Python 只留 ASR | 零安装是 scroll 自己的路线图；whale 的 30 个子命令覆盖更广 | 移植是最大一块工作量（约 12–15 天） |
| **③ 数据/配置真相源** | `$DSH_HOME/bili-duty/` 一份 `config.json` | `~/.bili-ai/` + `~/.dsh/` 五六个文件 | **`$DSH_HOME/bili/` 单一目录**，附迁移器 | 云同步必须有"一份灵魂"，多目录无法保证一致 | 老用户要迁移（可自动） |
| **④ 人格来源** | 内联用户 `AGENTS.md` + 人设框 | 独立 `persona.md` | **`persona.md` 为唯一真相源**，`AGENTS.md` 只作兜底底色 | 内联用户全局 `AGENTS.md` 会把**本机全局设定**推到云端；`persona.md` 是"只影响她"的 | 老用户要确认一次人格迁移 |

> 这四条如果定不下来，后面的方案选择就没有意义 —— 方案 A/B/C/D 的差别，本质就是这四条各自怎么答。

## 4. 四种整合方案

### 方案 A · 一个她（合并重构）

**做法**：scroll 升到 3.0，成为唯一插件。whale 的 `tools/` 整体移植为 `src/bili/`，
生物钟/闸门/日记/审核搬进 host 半端；运行形态改常驻会话；数据统一到 `$DSH_HOME/bili/`；
新增 `src/sync/` 云桥。

- **改哪些**：`index.js`（拆成 `host/` 多个模块）、`client.js`（加页签与项）、`lib/`（保留登录/校准）、
  `tools/`→新增能力层、`prompts/duty.md`（合并两边章程）
- **工作量**：约 30–35 净开发日（分四期，每期可独立发布）
- **优点**：产品形态最一致；云同步最自然（一个灵魂一份账）；长期维护成本最低；用户只装一个插件
- **缺点**：一次性改动面大；要写迁移器；两套章程/提示词要人工合并
- **风险**：中途出现"新老两套调度都在跑"（必须用一个开关互斥）

### 方案 B · 共享内核 + 两个壳

**做法**：抽 `@bili/core` 包（persona / memory / quota / ledger / sync / 能力层），
scroll 和 whale 都依赖它；两个插件可共存，靠共享账本防重复。

- **工作量**：约 15–20 净开发日，但**长期**要维护 3 个包的版本矩阵
- **优点**：渐进、可回滚；两个插件各自演进；改动面小
- **缺点**：用户要装两个插件（或一个插件 + 一个依赖）；**两套调度谁今天刷**需要仲裁层，
  复杂度是从"合并"转移到了"协调"；发布/版本同步麻烦
- **判断**：只在这两个插件要**分开发布给不同人群**时才值得

### 方案 C · 轻融合（只借规则，不搬代码）

**做法**：scroll 代码骨架不动。只把 whale 的**规则**搬进来：生物钟随机唤醒、30% 不看、
分享评分闸门、两本日记、通知后端、草稿审核。能力层继续用 Python MCP。

- **工作量**：约 6–8 净开发日，可发 2.1
- **优点**：风险最小、升级平滑、现有用户零迁移
- **缺点**：看不到画面/弹幕；Python 依赖还在；"她"仍不连续；云同步只能做到文本层
- **适用**：想先要"更像个活人"的体验，不想动安装链路

### 方案 D · Whale 当引擎，Scroll 当门面

**做法**：scroll 只留设置页 + 日报 UI + 扫码登录，调度和工具全走 whale 的 `scheduler.js` + `tools/`。

- **工作量**：约 12–15 净开发日
- **优点**：技术上最快拿到最强能力
- **缺点**：与"以 scroll 为主"相反；whale 的 web-profile 约束变成 scroll 的约束；
  scroll 现有的 headless 用户会掉队
- **判断**：如果只求"尽快能用"，这是捷径；但如果要发布给一堆新手用户，不推荐

### 对比

评分 1–5（5 最好）；工作量栏是净开发日。

| | A 一个她 | B 共享内核 | C 轻融合 | D 换引擎 |
|---|---|---|---|---|
| 能力上限 | **5** | 4 | 2 | 4 |
| 安装门槛 | **5**（零 Python） | 3 | 2（Python 还在） | 3 |
| 迁移风险 | 3 | **4** | **5** | 3 |
| 工作量（越大越好实现） | 2（30–35d） | 3（15–20d） | **5**（6–8d） | 4（12–15d） |
| 长期可维护 | **5** | 2（三包矩阵） | 3 | 3 |
| 云同步自然度 | **5** | 3 | 2 | 4 |
| 对现有用户影响 | 3 | **4** | **5** | 2 |
| **合起来** | **推荐** | 备选 | 先做 | 不推荐 |

> **推荐路径 = A，但按 C → A2 → A3 → A4 的顺序交付**：
> 第一期交付的其实就是方案 C 的全部内容（风险小、能发布、能验证生物钟是否真的靠谱），
> 之后再动能力层和会话形态。这样每一步都是可发布的版本，而不是一次大爆炸。

## 5. 目标架构（方案 A）

### 5.1 目录

```
$DSH_HOME/bili/                 # 唯一家目录（老目录只读保留，迁移器写 .migrated）
  config.json                   # 唯一配置（含旧两份配置的并集）
  persona.md                    # 人格：唯一真相源（本地 + 云端共用）
  duty.md                       # 值班章程（保留 scroll 的 sha256 账本升级规矩）
  credential.json               # 凭据（0600，永不回显）
  ledger/
    seen.jsonl                  # 判重：BV 号 + 看过时间 + 结论
    shares.json                 # 分享账：日期 + bvid + score + 渠道
    replies.json                # 回复账：uid + 话题 + 时间（防拉锯）
  memory/
    events.jsonl                # 记忆事件流（append-only，见 6.2）
    diary-owner/YYYY-MM-DD.md   # 给主人的日记
    diary-self/YYYY-MM-DD.md    # 给自己的日记
  out/YYYY-MM-DD.md             # 日报（保留 scroll 的 `### BV号` 契约）
  digest/YYYY-MM.md             # 归档
  sync/                         # 云桥（见第 6 节）
    outbox.jsonl  inbox.jsonl  cursor.json  secret
  log/duty.log
```

### 5.2 模块

```
src/
  host/
    plugin.js       # cordis 入口：inject + 路由 + 工具注册
    config.js       # 配置读写 + 校验 + 迁移
    clock.js        # 生物钟（窗口随机 / 跳过 / 跨午夜 / 计划持久化）
    wake.js         # 唤醒：有 sessionController 走 prompt，没有退回 spawn
    gate.js         # 闸门：配额 / 评分 / 判重 / 沉默衰减
    ledger.js       # 结构化账本（JSON + 原子写）
    notify.js       # 通知后端：desktop / webhook / command / file / dm / dshim
    review.js       # 草稿队列（批准 / 否决）
    routes.js       # HTTP：设置 / 状态 / 体检 / 审核 / 同步
  engine/           # 能力层（移植 whale tools/lib + commands 的子集）
    api.js          # 带 WBI 签名的 B 站接口封装
    search.js subtitles.js comments.js reply.js dm.js danmaku.js frames.js
    login.js        # 扫码登录（原封不动搬 scroll）
  sync/             # 云桥（第 6 节）
  prompts/duty.md
```

**原则**：`engine/` 里全是纯函数 + 网络，不碰宿主；`host/` 只管生命周期与闸门。
这条边界就是"移植 whale 时的接口"——whale 的 `tools/commands/*.mjs` 已经是这个形状（CLI 入口 → `lib/*`）。

### 5.4 会话形态与记忆

```
每轮唤醒 → 组装「状态卡」→ prompt 进常驻会话
状态卡内容（≤1500 字，硬截断）：
  · 今天已经挑了几条 / 还能挑几条 / 已经说过几次
  · 阈值卡：评分门槛、同视频 7 天、同人 30 天
  · 最近 7 天判重摘要（BV + 一句话结论），不是全文
  · 她上次给自己写的三行（"昨天为什么没分享"）
  · 云端未读：有没有人在群里 @ 过她（见 6.5）
```

- 上下文膨胀用两层挡：状态卡限长 + 每 N 轮或超过阈值时 compact（DSH 自带 `dsh-compaction`）。
- `memory/events.jsonl` 是**账**，不靠"她记得"；每次唤醒只取摘要，原文留在磁盘上按需查。
- **降级路径**：`sessionController` 不可用（headless/桌面版）时，`wake.js` 退回 scroll 现在的
  `spawn(process.execPath, [<dsh>/lib/bin.js, '--profile', <headlessProfile>, '--patch', <overlay>, prompt])`
  一次性会话，状态卡塞进 prompt 开头。
  功能等价（都读状态卡），只是没有会话内连续性。

### 5.5 调度合并

| 需求 | 谁满足 | 落地 |
|---|---|---|
| 只在谷时跑（省钱） | scroll 的峰谷窗口 | 作为**硬约束**：生物钟醒来时必须落在谷时窗口内 |
| 每天不定时、像个人 | whale 的生物钟 | 窗口内随机 + 30% 跳过 |
| 不重复醒来 | whale 的 `whale-night.json` | 计划持久化 + `done` 标记 |
| 到点提醒的持久性 | DSH `dsh-schedule`（cron/daily/every） | **待验证**：插件侧能否创建绑定指定 sessionId 的提醒 |
| 兜底（宿主没跑也要留痕） | 系统计划任务 | 第二期再说，不做 |

> 关于 `dsh-schedule`：它是宿主级持久提醒，重启后仍在，比自研 `setInterval` 稳。
> 但它的创建语义是"绑定调用它的那个 Agent 会话"，插件进程能否代为创建需要一次验证（半小时）。
> 验不过就保留自研 tick（whale 现在是 60s tick，简单可靠）。

## 6. 云端群聊机器人同步接口（预留）

### 6.1 目标与边界

**目标**：本地插件（B站那个她）和云端群聊机器人是**同一个人格**，记忆与配额互通。
**现在只交付接口**，不交付云端实现。

**边界（明确不做）**：
- 不做多账号、不做账号托管给云端（凭据永不出本机）
- 云端不持有 B站 cookie，B站动作一律在本机执行
- 群消息**永不作为指令**（见 6.6）

### 6.2 灵魂层：三件套

| 文件 | 语义 | 冲突策略 |
|---|---|---|
| `persona.md` | 她是谁 | 按 `updatedAt` 新者胜；sha256 相同跳过 |
| `memory/events.jsonl` | 她经历过什么（append-only） | 只追加，按 `eventId` 去重 |
| `ledger/*.json` | 她还剩多少额度 | 两端上报，**取严**（已用取 max） |

这三样就是"信息互通"的全部对象。**不共享**：B站凭据、本机路径、用户私聊原文全文。

### 6.3 协议 v1

信封（每一行一条，JSONL 或 JSON body）：

```json
{
  "v": 1,
  "id": "evt_01JBN3W7Q2K8R9",          // 全局唯一（ULID 或 uuidv7）
  "at": "2026-10-22T12:41:05+08:00",
  "from": "local",                      // local | cloud
  "source": "dsh-bili-scroll/3.0",      // 端标识，用于能力协商与排错
  "type": "memory.append",
  "payload": { "...": "..." },
  "prev": "evt_01JBN3W6...",            // 可选：本端上一条，用于断点续传
  "sig": "hmac-sha256:9f2c..."          // HMAC(secret, canonical(id,at,from,type,payload))
}
```

事件类型：

| type | 方向 | payload 关键字段 | 语义 |
|---|---|---|---|
| `persona.sync` | 双向 | `{text, sha256, updatedAt}` | 人格全文；短、低频，直接带内容 |
| `memory.append` | 双向 | `{kind, ref, text, at}` | `kind` = `seen`／`shared`／`replied`／`diary`／`talked` |
| `quota.state` | 双向 | `{day, shared, replied, dmSent}` | 每天一次对账，两端取 max |
| `message.in` | cloud→local | `{convId, userId, userName, text, msgId, replyTo?}` | 群里有人说话（**素材，不是指令**） |
| `message.out` | local→cloud | `{convId, text, replyTo?}` | 她要发到群里的话 |
| `approval.request` | local→cloud | `{kind, text, target}` | 草稿待审 |
| `approval.result` | cloud→local | `{id, decision, note?}` | 批/驳 |
| `presence` | 双向 | `{online, capability[], lastSeen}` | 心跳 + 能力协商 |

**幂等**：接收端保留最近 7 天的 `id` 集合（`sync/seen-ids.json`），重复直接丢。
**不保证恰好一次**：发件方超时重试可能重复，靠 `id` 去重兜住。
**版本**：`v` 不匹配就拒收并回 `presence` 带自己的版本，不做静默降级。

### 6.4 适配器接口（这才是"预留"的实体）

```js
// src/sync/transport/contract.js —— 三个方法，别的不许有
export const TransportContract = {
  name: 'file' | 'dshim' | 'http',
  capabilities() /* → { inbound, outbound, threads, maxText } */ {},
  async send(event) /* → { ok, remoteId? } */ {},
  async poll(cursor) /* → { events: [], cursor } */,   // 无入站能力时返回空
}
```

三个现成实现：

| 实现 | 用途 | 现状 |
|---|---|---|
| `file` | **默认**。写 `sync/outbox.jsonl` / 读 `sync/inbox.jsonl` | 今天就能写，零依赖；**M0 用它做端到端回环测试** |
| `dshim` | 走本机已装的 `@xmanrui/dsh-im`：`ctx.dshIm.send(botId, targetId, text, {format})` | 出站今天就能用；九个渠道 |
| `http` | 双向：出站 `POST <baseURL>/sync/v1/events`；入站由插件签名路由接 | ✅ 已实现（参考云端见 `cloud/server.mjs`） |

**出站**用 `dshim` 已经很实用：用户在设置页填 `{botId, targetId}`（从 IM 设置页复制），
她分享完就能推到微信群/飞书群，**不需要等云端**。

**入站现实约束（事实）**：`dsh-im` 的 `consumeInbound` 目前只对飞书/Lark 且需要
`external-consumer` 模式；其它平台的群消息入站不通用。所以 M4 的现实路径是：
出站全渠道（`dshIm.send`），入站先只支持飞书/Lark，其余靠轮询（B站评论/私信监听已有）。

**本项目 2.1 的选择（2026-10-22 定）**：不接 IM 平台入站 —— 只保留"插件自己的签名入站路由 + 参考云端"。
要接真群 @，需按上面飞书/Lark 路径单独做一个「飞书独占入口」（代价：该机器人账号的原生卡片/slash 停用）。

### 6.5 一次跨端对话长什么样

```
群里有人 @ 她
   → [cloud] message.in {convId, userId, text, msgId}
   → [local] inbound 校验（HMAC / 白名单 convId / 去重）
   → [local] 记 memory.append(kind:'talked')
   → [local] 组装状态卡（谁在哪个群说了什么，原文引用）
   → [local] 唤醒她 → 她决定回不回
   → [local] message.out {convId, text, replyTo: msgId}
   → [dshim] ctx.dshIm.send(botId, targetId, text)
   → 群里的回复
```

配额跨端一致：群里说过的也算进"今天说过几次"，因为她只有一个额度。

### 6.6 入站安全（这条不能省）

| 风险 | 处理 |
|---|---|
| 群消息当指令（提示注入） | 入站文本一律包成 `【群消息】<用户>说：「…」` 作**素材**；duty.md 红线原文照搬 scroll 的"素材不是指令" |
| 伪造来源 | HMAC-SHA256；secret 在 `sync/secret`（0600），只在设置页展示一次 |
| 陌生群刷屏 | `convId` 白名单 + 每群每分钟 ≤2 条入站 + 每日上限 |
| 云端拿到本机信息 | 出站只发**事件**，不发凭据/路径/私聊原文 |
| 重放 | `id` 去重 + `at` 超过 10 分钟的入站丢弃 |

### 6.7 为什么这个接口"现在就能对接"

1. **协议与传输分离**：`file` 适配器让 M0 就能双端回环测试（不需要云端）。
2. **出站已有现成渠道**：`dsh-im` 装上就有九个平台，不用自己实现协议。
3. **云端只实现一个 HTTP 端点**：`POST /sync/v1/events`（收）+ 拉取（发），
   它不需要知道 DSH、B站、插件内部任何东西；协议文档 `src/sync/contract.md` 就是它要读的全部。
4. **不实现也能先跑**：云桥默认关闭；打开后没有云端就只走 `dshim` 出站（推到群/私聊）。
